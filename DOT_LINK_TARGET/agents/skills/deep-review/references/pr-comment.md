# PR へのコメント投稿

**この手順は `--comment` 付きで起動されたか、ユーザーがこの会話で投稿を明示的に指示したときだけ実行する。**
ローカル表示しか頼まれていないときに、ここに書かれたコマンドを実行してはいけない。

## 1. 投稿直前の再確認

```bash
gh pr view <n> --json state,isDraft,headRefOid,url
gh api repos/{owner}/{repo}/pulls/<n>/reviews --jq '.[] | select(.user.login=="<自分>") | {id, commit_id}'
```

- `state` が `CLOSED` / `MERGED` → 投稿しない。ユーザーにその旨を伝えて終わる。
- `headRefOid` がレビュー時の SHA と違う → 新しいコミットが積まれている。投稿せず、再レビューするかユーザーに確認する。
- 自分が同じ head SHA に対して既に deep-review のレビューを付けている → 重複投稿しない。

## 2. 投稿対象の選び方

指示の仕方で決まる。

| 指示 | 投稿対象 |
|---|---|
| 結果を見たあとで「コメントして」「読みやすくしてコメントして」とだけ言われた | 手順 6 でローカルに表示した指摘すべて（CONFIRMED・PLAUSIBLE・nit）。REFUTED は含めない |
| 件を指定された（「〇〇以外」「2 と 3」など） | 指定された件だけ |
| 起動時に `--comment` を付けられた（結果を見る前） | CONFIRMED かつ confidence 80 以上だけ |

- 指定の中に REFUTED が含まれていたら、反証で除外した理由を 1 行添えて、本当に投稿するか確認する。
- 対象が 0 件なら投稿しない。「問題は見つかりませんでした」もコメントしない（PR がノイズで埋まるため）。
- 再レビューで「継続中」の指摘は、新しいコメントを付けず、前回のスレッドに返信するか、何もしない（言い換えて重複させない）。
- 「コンフリクト」などの事実は、この PR が原因のものだけ本文に書く。親 PR から引き継いだものは書かない。
- スタックの親 PR に自分が付けた指摘と同じ問題がこの PR に引き継がれている場合は、言い換えて新しく書かず、
  この PR で何が新たに起きるか（新しく足した KDoc の約束と食い違う、など）だけを書き、親 PR のコメントへのリンクを添える。
- 変更していない行が原因の指摘や、申し送り・チケット番号など手続きの指摘は、インラインではなくレビュー本文の末尾に書く。

## 3. 行番号と引用の確認

サブエージェントが報告した行番号はずれていることがある。ずれたまま投稿すると 422 になるか、別の行にコメントが付く。
worktree は手順 6 の後に削除していることが多いので、worktree ではなく `git show` で読む。

```bash
git show <head SHA>:<path> | grep -n '<指摘箇所に特徴的な文字列>'
git show <head SHA>:<path> | sed -n '<start>,<end>p'
```

- コメントを付ける行だけでなく、**本文中で引用する行番号・ファイル名・テスト名・ガイドラインの文言**も実ファイルで確かめる。
- 複数行にまたがる指摘は `start_line` / `line` で範囲を指定する。
- その行が diff のハンクに含まれるかも確かめる（新規ファイルなら全行が対象。既存ファイルは `git diff -U0 <merge-base> <head SHA> -- <path>` の `@@` で確認）。
- 指摘の原因が diff 外の行にある場合（baseline に残ったエントリなど）は、原因を生んだ変更行（その違反を解消した関数など）に付ける。
  それも無ければレビュー本文に書く。

## 4. 投稿方法

変更行に紐づけられる指摘は**インラインのレビューコメント**、紐づけられない指摘は**レビュー本文**に入れ、
1 回のレビューとしてまとめて投稿する。`event` は必ず `COMMENT`（`REQUEST_CHANGES` / `APPROVE` は使わない）。

ペイロードは JSON ファイルに書いてから渡す（シェルのエスケープ崩れを防ぐ）。書いたあと `python3 -c "import json; json.load(open('<file>'))"` で形を確かめる。

```bash
gh api repos/{owner}/{repo}/pulls/<n>/reviews \
  --method POST \
  --input <scratchpad>/review.json
```

```json
{
  "commit_id": "<head SHA>",
  "event": "COMMENT",
  "body": "<レビュー本文>",
  "comments": [
    { "path": "src/foo.ts", "line": 42, "side": "RIGHT", "body": "<指摘本文>" },
    { "path": "src/bar.ts", "start_line": 10, "start_side": "RIGHT", "line": 14, "side": "RIGHT", "body": "<指摘本文>" }
  ]
}
```

- 422 エラー（行が diff に無い等）が返ったら、全指摘を本文に入れたまとめコメント（`gh pr comment <n> --body-file <file>`）に切り替える。

## 5. 文面の書き方

「読みやすく」が既定。レビューを受け取る人が、どれを直すべきかを最初の数行で判断でき、各コメントだけ読んでも何が起きるか分かるように書く。

### ラベル（Conventional Comments）

各コメントの先頭に、太字でラベルと装飾を付ける（https://conventionalcomments.org/ ）。

| 指摘 | ラベル |
|---|---|
| CONFIRMED の blocker / critical / major | `**issue (blocking):**` |
| CONFIRMED の minor | `**issue (non-blocking):**` または改善の提案なら `**suggestion (non-blocking):**` |
| PLAUSIBLE（確かめきれていない） | `**question (non-blocking):**`（高影響なら `**question (blocking):**`） |
| nit | `**nitpick (non-blocking):**` |

### 各コメント

1. 1 文目で、何が問題かを言い切る（ラベルの直後）。
2. 何が起きるか: 具体的な入力や状態と、その結果。実測値があれば書く。
3. どう直すか: 修正案を 1〜2 文。複数の選択肢があれば並べる。
4. 必要なら根拠のリンク（完全な SHA と行範囲 `https://github.com/<owner>/<repo>/blob/<full-sha>/<path>#L<start>-L<end>`、一次資料の URL）。

書き方の注意:

- 平文で書く。太字は先頭のラベルだけにし、「問題点:」「失敗シナリオ:」のような見出しを並べない。
- 実害がない・今の呼び出し元では起きない場合は、そう明記する（受け取る人が優先度を判断できるように）。
- 確かめきれていない事実は断定せず、「確認させてください」「〜は確認できていません」と書く。
- 依頼は「〜してもらえますか」「〜してもらえると助かります」の形にし、命令形にしない。
- 絵文字は使わない。

### レビュー本文

```
## Code review (deep-review)

<N> 件コメントしました。<マージを止めるものがあるかを 1 文で>

- 直してほしいもの: <issue の要旨>
- 確認してほしいもの: <question の要旨>
- 任意: <suggestion・nitpick の要旨>

<良かった点・問題がなかった範囲を 1 文（例: 判定ロジック本体は問題ありませんでした）>
<この PR が原因の事実があれば 1 文（例: develop と〇〇がコンフリクトします）>
<diff 外の指摘があれば、インラインと同じ書き方で番号付きで列挙>
```

空になる区分の行は省く。

## 6. 報告

投稿後、作成されたレビューの URL（レスポンスの `html_url`）と各コメントの URL を表にしてユーザーに伝える。
あわせて次を書く。

- 投稿前に確認したこと（PR の状態・head SHA・行番号・引用の修正があればその内容）
- 投稿の基準（どの指示に従って何を投稿したか。既定の基準に届かない指摘を含めたならそのこと）
- 投稿しなかった指摘（REFUTED など）とその理由
