# PR へのコメント投稿

**この手順は `--comment` 付きで起動されたか、ユーザーがこの会話で投稿を明示的に指示したときだけ実行する。**
ローカル表示しか頼まれていないときに、ここに書かれたコマンドを実行してはいけない。

## 1. 投稿直前の再確認

```bash
gh pr view <n> --json state,isDraft,headRefOid,url
```

- `state` が `CLOSED` / `MERGED` → 投稿しない。ユーザーにその旨を伝えて終わる。
- `headRefOid` がレビュー時の SHA と違う → 新しいコミットが積まれている。投稿せず、再レビューするかユーザーに確認する。
- 自分（`gh api user --jq .login`）が同じ head SHA に対して既に deep-review のコメントを付けている → 重複投稿しない。

## 2. 投稿対象の選別

- CONFIRMED かつ confidence 80 以上の指摘だけを投稿する。
- 対象が 0 件なら投稿しない。「問題は見つかりませんでした」もコメントしない（PR がノイズで埋まるため）。
- **例外: ユーザーが投稿する指摘を明示的に指定したとき**（「〇〇以外をコメントして」「2 と 3 をコメントして」など）は、
  上の基準よりその指定を優先する。PLAUSIBLE や nit、未検証の指摘も、指定されたものは投稿してよい。
  - 基準は「何も指定されていないときの既定」であり、ユーザーが結果を見たうえで選んだ指摘を止める理由にはならない。
  - REFUTED の指摘が指定に含まれていたら、反証で除外した理由を 1 行添えて、本当に投稿するか確認する。
  - コメントの重大度ラベルは検証後の値（例: PLAUSIBLE で下がったものは `minor/nit`）で書き、実態より強く見せない。
  - 投稿後の報告で、基準に届かない指摘を指定に従って投稿したことを 1 行明記する。

## 3. 行番号の確認

サブエージェントが報告した行番号はずれていることがある。ずれたまま投稿すると 422 になるか、別の行にコメントが付く。
投稿する指摘ごとに、レビュー時の head SHA のファイルを読んで、コメントを付ける行を確かめる。
worktree は手順 6 の後に削除していることが多いので、worktree ではなく `git show` で読む。

```bash
git show <head SHA>:<path> | grep -n '<指摘箇所に特徴的な文字列>'
git show <head SHA>:<path> | sed -n '<start>,<end>p'
```

- 複数行にまたがる指摘は `start_line` / `line` で範囲を指定する。
- その行が diff のハンクに含まれるかも確かめる（新規ファイルなら全行が対象。既存ファイルは `git diff <merge-base> <head SHA> -- <path>` で確認）。

## 4. 投稿方法

変更行に紐づけられる指摘は**インラインのレビューコメント**、紐づけられない指摘（diff 外の行、ファイル横断の問題）は**レビュー本文**に入れ、
1 回のレビューとしてまとめて投稿する。`event` は必ず `COMMENT`（`REQUEST_CHANGES` / `APPROVE` は使わない）。

ペイロードは JSON ファイルに書いてから渡す（シェルのエスケープ崩れを防ぐ）。

```bash
gh api repos/{owner}/{repo}/pulls/<n>/reviews \
  --method POST \
  --input <scratchpad>/review.json
```

`review.json` の形:

```json
{
  "commit_id": "<head SHA>",
  "event": "COMMENT",
  "body": "<レビュー本文>",
  "comments": [
    { "path": "src/foo.ts", "line": 42, "side": "RIGHT", "body": "<指摘本文>" }
  ]
}
```

- `line` は変更後ファイルの行番号で、diff のハンクに含まれている必要がある。含まれない指摘は `comments` に入れず本文に回す。
- 422 エラー（行が diff に無い等）が返ったら、全指摘を本文に入れたまとめコメント（`gh pr comment <n> --body-file <file>`）に切り替える。

## 5. 書式

簡潔に書き、絵文字は使わない。コードへのリンクは完全な SHA と行範囲で書く
（`https://github.com/<owner>/<repo>/blob/<full-sha>/<path>#L<start>-L<end>`）。

インラインコメント:

```
**[<severity>]** <問題点>

失敗シナリオ: <入力/状態> → <誤った結果>

<根拠: ガイドラインの引用 / 過去 PR・コミットへのリンク（あれば）>

修正案: <短く>
```

レビュー本文:

```
## Code review (deep-review)

<N> 件の指摘があります（多観点レビュー後、別エージェントによる反証で確認済みのもの）。

<diff 外の指摘があれば、インラインと同じ書式で番号付きで列挙>
```

## 6. 報告

投稿後、作成されたレビューの URL（レスポンスの `html_url`）をユーザーに伝える。
投稿しなかった指摘（PLAUSIBLE、confidence 80 未満）がある場合は、件数とローカルで確認できることを 1 行添える。
