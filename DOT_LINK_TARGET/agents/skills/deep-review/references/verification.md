# 敵対的検証（指摘の反証）

レビュアーが出した指摘を、別のサブエージェントに**否定させる**。
否定しきれなかった指摘だけが報告に残る。誤検知を鵜呑みにして直すと、動いていたコードを壊すほうが高くつくため。

## 渡すもの・渡さないもの

- 渡す: 指摘 1 件（または同一ファイルの指摘数件）、作業ディレクトリのパス、diff の取得コマンド、ガイドラインファイルのパス一覧、
  後続ブランチ名（呼び出し元の確認に使う）、PR 本文を読むコマンド（作者の実測値などの事実確認に使う）
- 渡さない: レビュアーの他の指摘、どの観点から出たか、この会話の経緯（検証者が引きずられて擁護/同調するのを防ぐ）
- 否定の材料は、指摘の内容に合わせて具体的に挙げる（「呼び出し元を読め」「この資料と照合せよ」など）。
  汎用の材料だけだと、検証が浅くなる

## 指示テンプレート

```
以下のコードレビュー指摘は誤検知かもしれません。あなたの仕事はこの指摘を**否定する**ことです。
実際のコードを読み、指摘された失敗シナリオが本当に成立するかを確かめてください。
リポジトリの追跡ファイルは変更せず、GitHub にも書き込まないでください。一時ファイルは <scratchpad> 配下に置いてください。

否定の材料になるもの:
- 呼び出し元・既存のバリデーション・型・フレームワークやライブラリの保証によって、そのシナリオに到達しない
- 失敗シナリオの前提（入力・状態）が現実には発生しない
- 指摘が引用しているガイドライン/コメント/過去 PR/行番号が、実際にはそう言っていない、または別の箇所の話である
- 指摘が比べている基準（設定値・許容数など）が古い（merge-base 時点の値で、最新のベースでは変わっている）
- 問題は変更前から存在しており、この diff が生んだものではない
- lint・型チェック・CI が確実に検出する種類の問題である
- 提案された修正（別ライブラリへの置き換えなど）を適用すると、別の不整合が入る
<指摘に合わせた具体的な否定の材料>

可能なら、テストや小さなスクリプトで再現を試みてください。ビルドやテストを走らせるなら対象を絞り、1 回 10 分を上限にしてください。
外部システムの挙動を根拠にするときは一次資料の URL を示し、確かめられなければ「未確認」と書いてください。
判断が付かない場合は REFUTED ではなく PLAUSIBLE にしてください。

## 指摘
<severity / file:line / 問題点 / 失敗シナリオ / レビュアーが示した根拠>

## 対象
- 作業ディレクトリ: <path>
- diff の取得: <コマンド>
- ガイドラインファイル: <パス一覧>
- 後続ブランチ（あれば）: <ブランチ名>

## 出力
- verdict: CONFIRMED | PLAUSIBLE | REFUTED
- confidence: 0 / 25 / 50 / 75 / 100（下のルーブリック）
- 根拠: 実際に読んだコード（file:line）や実行結果に基づく説明。CONFIRMED なら再現手順
- 影響: データ損失・セキュリティ・誤った権限付与につながるか（つながる / つながらない / 未確認）
- severity の見直し: レビュアーの重大度が過大/過小なら修正後の値と理由
- 気づいた事実（あれば）: 指摘とは別に見つけた事実（コンフリクト、CI の状態など）
```

## 判定

- **CONFIRMED** — 失敗シナリオの成立をコードまたは実行で確認できた
- **PLAUSIBLE** — 否定する材料が見つからないが、成立も確認しきれない
- **REFUTED** — 上の「否定の材料」のいずれかで成立しないと示せた

## 確信度ルーブリック（公式 code-review plugin の基準を踏襲。検証者にそのまま渡す）

- **0**: まったく確信がない。軽い精査にも耐えない誤検知、または既存の問題
- **25**: やや確信がある。本物かもしれないが確認できなかった。スタイルの指摘で、ガイドラインに明記されていないもの
- **50**: そこそこ確信がある。本物だと確認できたが、細かい指摘か、実際にはめったに起きない
- **75**: 強い確信がある。再確認し、実際に踏む可能性が非常に高いと分かった。機能に直接影響する、またはガイドラインが明示している問題
- **100**: 確実。再確認して本物であり、頻繁に起きることを証拠が直接示している

## 高影響の例外

通常は「迷ったら報告しない」が、影響が「つながる」の指摘（データ損失・セキュリティ・誤った権限付与）は例外として扱う。

- PLAUSIBLE でも、確信度が 25 でも、「要確認」の先頭に出す。何が確認できていないかを 1 行で添える。
- REFUTED でも、否定の根拠が「前提が現実には起きないはず」という推定だけなら、PLAUSIBLE に戻して扱う。
  否定の根拠をコードや一次資料で示せている場合だけ除外する。

## 結果の扱い

| verdict | ローカル表示 | PR 投稿（`--comment` で起動したとき） | PR 投稿（結果を見たあとで指示されたとき） |
|---|---|---|---|
| CONFIRMED（confidence 80 以上） | 指摘として表示 | 対象 | 対象 |
| CONFIRMED（80 未満） | 指摘として表示 | 対象外 | 対象 |
| PLAUSIBLE | 「要確認」として表示 | 対象外 | 対象（`question` として） |
| REFUTED | 除外。要旨と理由を 1 行ずつ表示 | 対象外 | 対象外（指定されたら理由を添えて確認） |

REFUTED が全体の半分を超えた場合は、レビュアーが過検知気味であることを結果表示の冒頭で 1 行伝える。
