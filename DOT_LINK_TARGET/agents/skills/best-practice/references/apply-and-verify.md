# 提案の反映と検証

`../SKILL.md` から、ユーザーが ID や番号で提案への対応を指示したときに読む。

## 手順

1. 反映前に対象ファイルの現状を読み直す。提案時から他セッションで変わっていることがある
2. 変更は提案の範囲に絞る。提案と違う形で反映するときは、理由を報告に書く
3. 下表の方法で検証する。検証できないもの（実ファイルを読まないと確かめられない deny など）は、未確認として報告する
4. 報告では「確認済み」と「未確認」を分けて書く。本番の自動実行でしか確かめられないものは、次回どこを見ればよいかを書く
5. コミットはリポジトリごとに分ける（`~/.claude` 配下は Dotfile、プロジェクト配下はそのリポジトリ）。commit-draft の形式でスクリプトにし、ユーザーに `!` で実行してもらう
6. `history.md` の該当行の状態（実施 / 見送り）と理由を更新する

## 検証方法

| 変更の種類 | 検証方法 |
|---|---|
| フック | 見本の JSON を stdin に流して exit code を見る。止めたいケースと通したいケースの両方を試す |
| エージェント frontmatter の hooks | YAML から command を取り出し（`ruby -ryaml` など）、上と同じように流す |
| CLI フラグ | 安いモデルで `claude -p "Reply with just OK" <フラグ> --model haiku` を流し、通るか確かめる |
| autoMode | `claude auto-mode config` で実効値を見る。別ファイルは `claude --settings <file> auto-mode config` |
| スキル一覧（skillOverrides・プラグイン無効化など） | 対象ディレクトリで新しい `claude -p --model haiku` を起動し、一覧に載っているスキル名を present/absent で答えさせる。変更前と後を比べる |
| settings.json | `jq empty` で JSON として読めるか確かめる |
| シェルスクリプト | `bash -n` で構文を確かめる |

## コミット用スクリプトの置き場所

- `/tmp/commit-draft.sh` のような共有パスは、並行する別セッションに上書きされる（2026-10-02 に実例）
- スクラッチパッドの長いパスは、端末で折り返されて `!` での実行が壊れる（2026-10-02 に実例）
- `/tmp/cc<セッションIDの先頭6桁>-<連番>.sh` のように、短くてセッション固有のパスに置く。実行後は消す
