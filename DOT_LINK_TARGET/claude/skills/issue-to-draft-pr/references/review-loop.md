# ゼロベースレビュー → 反証 → 修正 → push ループ

Draft 中に CI が走らないリポジトリでは、このループが実質的な品質ゲートになる。
やることは単純で、「実装した自分」とは独立した視点で diff を厳しく見て、重大な問題を潰してから人間レビューに渡せる状態にすること。

## なぜ独立サブエージェントなのか

実装した本人がレビューすると、「こう動くはず」という先入観で見てしまい、境界条件・エラーパス・規約違反を見逃す。
実装の文脈を持たないサブエージェントに diff だけを渡すと、ゼロベース（白紙）で読めるので、コードが実際に語っていることだけを評価できる。

## 敵対的検証という構え

「このコードは正しそうか？」と問うレビューは、正しく見える理由を探しにいくので簡単に通ってしまう。
知りたいのは逆で、**このコードはどう壊れるか**。だからレビュアーには「壊す側」に立たせる。

これを 2 方向で効かせる。

1. **実装を反証する（レビュー時）** — 各変更点について「どんな入力・状態ならこの実装は誤った結果を返すか」を具体的に構成させる。
   空・null・0 件・巨大件数、同時実行、外部 API のエラー/タイムアウト/部分成功、権限のないユーザー、既存データとの不整合、
   リトライ時の二重適用あたりが定番の切り口。
   指摘には必ず**失敗シナリオ（具体的な入力/状態 → 誤った結果）**を書かせる。これを書けない指摘は、たいてい実在しない問題か、単なる好みである。
2. **指摘を反証する（修正前）** — LLM レビューは自信満々に存在しない不具合を報告する。指摘を鵜呑みに直すと、動いていたコードを壊す方が高くつく。
   そこで `blocker` / `critical` / `major` は、**別の**サブエージェントに「この指摘を否定せよ」と依頼し、実コードで再現できるかを確かめてから修正に入る。

### 指摘の反証の回し方

レビュー結果が出たら、`blocker` / `critical` / `major` の各指摘ごとに反証エージェントを立てる（複数あるなら並列でよい）。
渡すのは「指摘 1 件」と「diff」と「実際のコードを読める環境」だけ。レビュアーの他の指摘や実装意図は渡さない（同調を防ぐため）。

```
以下のレビュー指摘は誤検知かもしれません。あなたの仕事はこの指摘を**否定する**ことです。
実際のコードを読み、指摘された失敗シナリオが本当に成立するかを確認してください。
呼び出し元・既存のバリデーション・型・フレームワークの保証によって既に防がれているなら、それは誤検知です。
判断が付かない場合は REFUTED ではなく PLAUSIBLE にしてください。

## 指摘
<severity / file:line / 問題点 / 失敗シナリオ>

## 出力
- verdict: CONFIRMED（再現手順まで示せた） | PLAUSIBLE（否定しきれない） | REFUTED（成立しない）
- 根拠: 実際に読んだコード（file:line）に基づく説明
```

判定の扱い:

- **CONFIRMED** — 修正する。
- **PLAUSIBLE** — 原則修正する。ただし修正コストが大きい場合は、根拠を添えてユーザーに判断を仰ぐ。
- **REFUTED** — 修正しない。「なぜ誤検知だったか」を 1 行残す（同じ指摘が次ラウンドで再燃したときに再判断しなくて済む）。

反証にもコストがかかるので、`minor` / `nit` は対象外でよい。直しても壊れにくく、誤検知でも被害が小さいため。

## レビューの実行

`code-review` スキルや `feature-dev:code-reviewer` サブエージェントが使えるならそれを土台にしてよい。
ただし**issue の要件とリポジトリの実装ガイドを必ず文脈として渡す**こと。
レビュー観点が「一般的なコード品質」だけだと、要件未達やそのリポジトリ固有の規約違反を見逃す。

サブエージェントへの指示テンプレート:

```
あなたはこのリポジトリの独立レビュアーです。実装者ではないので、先入観なくゼロベースでレビューしてください。
「正しそうか」ではなく「どう壊れるか」を探してください。各変更点について、この実装が誤った結果を返す具体的な入力・状態を能動的に構成してください。
実装が正しく見えるときこそ、それを反証する入力を 1 つは試みてください。

## レビュー対象
<git diff origin/<base>...HEAD の内容、または PR の diff>

## issue の要件
<フェーズ0 で要約した要件・受け入れ条件（issue に明記が無く自分で置いた前提も含めて渡す）>

## このリポジトリの規約
<CLAUDE.md / AGENTS.md / CONTRIBUTING.md 等の該当箇所、対象モジュールのガイド>

## 評価基準
1. 要件充足: issue の受け入れ条件を満たしているか。漏れ・誤解はないか
2. 正しさ: バグ・ロジック誤り・境界条件・エラーパス・null/例外処理
   （空/0件/巨大件数、同時実行、外部 API のエラー・タイムアウト・部分成功、リトライ時の二重適用、既存データとの不整合を必ず当たる）
3. リポジトリ規約への準拠（上に渡したガイド、および周囲の既存実装のパターン）
4. パフォーマンス/計算量・メモリ効率（N+1、不要なフルロード等）
5. セキュリティ（インジェクション、認可漏れ、秘密情報の混入）
6. 後方互換性・移行（公開 API・DB スキーマ・設定の破壊的変更が紛れていないか）
7. テスト: 変更に見合うテストがあるか。追加された分岐が実際にカバーされているか
8. 可読性・既存パターンとの一貫性

## 出力フォーマット
各指摘を以下で返す（重大度を必ず付ける）:
- severity: blocker | critical | major | minor | nit
- file:line
- 問題点
- 失敗シナリオ: 具体的な入力/状態 → 実際に起きる誤った結果（nit 以外は必須。書けないなら指摘として出さない）
- 推奨する修正
最後に「重大度別の件数サマリ」を付ける。問題がなければ「指摘なし」と明記する。
無理に件数を稼がないこと。壊れる筋道を示せない指摘は、後段の反証で落とされるだけで、ノイズになる。
```

## 重大度ルーブリック

- **blocker**: マージ不可。ビルド/テストが壊れる、要件を満たさない、データ破壊・セキュリティ重大欠陥
- **critical**: 高確率で本番障害になるバグ・認可漏れ・重大なパフォーマンス劣化
- **major**: 直すべき明確な問題（ロジックの穴、規約違反、テスト不足）だが即障害ではない
- **minor**: 改善が望ましい（可読性、軽微な重複、命名）
- **nit**: 好みレベル・任意

## 修正方針

- `blocker` / `critical` / `major` は**反証を通してから**修正する（REFUTED は直さない）。
- `minor` / `nit` は妥当なら直す。見送る場合は「なぜ見送るか」を 1 行残す（過剰修正を避ける）。
- 修正が issue のスコープを超えるなら、その場で広げずユーザーに確認する。レビューは PR を膨らませる口実ではない。
- 修正後、変更モジュールのローカル検証（lint/test）を再度回してから push する。

## 停止条件（無限ループ・過剰修正の防止）

- `blocker` / `critical` が **0** になったら終了。残った `major` 以下はユーザーに一覧で報告する。
- **最大 3 ラウンド**。3 ラウンド回しても `blocker`/`critical` が消えない場合は打ち切り、残課題・原因の見立て・選択肢を添えてユーザーに判断を委ねる。
  - 同じ指摘が消えない、修正で別の指摘が増え続ける、といった堂々巡りは設計レベルの問題のサイン。手を動かし続けるより一度止める。
- 各ラウンドで「指摘 / 反証結果（CONFIRMED・PLAUSIBLE・REFUTED の内訳）/ 対応 / 残件」を 1 ブロックに要約し、進捗を可視化する。
  REFUTED が多いラウンドはレビュアーが過検知気味なので、次ラウンドでは失敗シナリオの具体性をより強く求める。

## Draft で CI が走るリポジトリの場合

フェーズ 0.5 で「Draft でも CI が走る」と分かっているなら、push 後に結果を取り込む。

```bash
gh pr checks <number> --watch
```

CI の失敗は事実（反証不要）なので、レビュー指摘より優先して直す。
CI が拾える種類の問題（lint / 型 / テスト失敗）はレビュアーに探させるまでもないので、レビューは論理・要件・設計に集中させる。

## ループ内の push

- 修正コミットはリポジトリのコミット規約に合わせる（Conventional Commits なら `fix: レビュー指摘対応 - <要点>` など）。
- Draft のまま push する。Draft 解除・force push はしない（ユーザーの明示指示があるときだけ）。
