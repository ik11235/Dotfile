# GitHub issue → Draft PR 自走ワークフロー

1 枚の GitHub issue を「動く Draft PR + 自己レビュー済み」の状態まで持っていくためのスキル。
目的はユーザーのコンテキストスイッチを最小化することなので、各フェーズで「次に何が起きるか」を明示しながら進める。

このスキルは**特定のリポジトリを前提にしない**。ベースブランチ・命名規約・検証コマンド・PR テンプレートは
フェーズ 0.5 でそのリポジトリから読み取る。憶測で `develop` や `npm test` を決め打ちしない。

## 大原則（なぜこの順序か）

- **承認ゲートを 1 回だけ置く**: issue 理解と影響調査が終わった「実装計画」の時点で必ず止まり、ユーザーの承認を得てから実装に入る。
  方針がズレたまま実装すると手戻りが最大になるため、ここだけは自走しない。
- **Draft では CI が走らないことがある**: 多くのリポジトリは重い CI を `draft == false` に限定している。
  その場合 Draft 中は CI が品質を守ってくれないので、push 前のローカル検証と push 後のゼロベースレビューが品質の砦になる。
  走るのか走らないのかはフェーズ 0.5 で確認する（`references/repo-conventions.md`）。
- **レビューは「実装した自分」とは別人格でやる**: 実装の文脈を持ったまま自己レビューすると先入観で見逃す。
  独立したサブエージェントに diff だけを渡し、ゼロベースかつ敵対的に指摘させる（`references/review-loop.md`）。
- **そのリポジトリの流儀に合わせる**: `CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` / `.github/` がそのリポの規約。
  自分の好みではなく、周囲のコードと地続きに見える実装を書く。

## フェーズ全体像

```
0.   issue 取得・理解
0.5  リポジトリ規約の把握（初回のみ）
1.   影響調査 → 実装計画提示 → 【承認ゲート】 ← ここで必ず止まる
2.   ブランチ作成
3.   実装（+ ローカル検証）
4.   Draft PR 作成
5.   ゼロベースレビュー → 指摘の反証 → 修正 → push  ┐
     （重大度しきい値 or 最大ラウンドに達するまで繰り返す）┘
6.   完了報告
```

---

## フェーズ 0: issue 取得・理解

1. 入力から issue 参照を抽出する。URL・`#123`・`owner/repo#123` のいずれも受け付ける。
   リポジトリ指定がなければカレントディレクトリのリポジトリとみなす（`gh repo view --json nameWithOwner`）。
2. `gh issue view` で本文・コメント・ラベル・担当者・関連 PR まで読む。
   ```bash
   gh issue view <number> --json number,title,body,state,labels,assignees,comments,milestone,url
   ```
3. **着手前チェック（重要・無駄な再実装の防止）**: 実装に入る前に「この issue は既に対応済みでないか」を必ず確認する。
   別の人・別ブランチで実装済み／PR 化済み／マージ済みのことがある。
   - issue の state とコメントの最新状況、`closed` でなくても「対応中」の宣言がないか
   - 既存 PR・ブランチ: `gh pr list --search "<number>" --state all`、`git branch -a | grep <number>`、
     `git log --oneline <base>..origin/HEAD | grep -i "#<number>"`
   - 既に実装/マージ済みと分かったら、**実装せずその事実を申し送り**、何を求めているのか
     （再レビューだけか、追加対応か、クローズ確認か）をユーザーに確認する。
4. issue の「何を・なぜ・受け入れ条件」を自分の言葉で 2〜4 行に要約する。再現手順・期待挙動・関連 issue/PR があれば拾う。
   issue はチケットと違って**受け入れ条件が書かれていないことが多い**。書かれていなければ、
   自分が満たすべきと考える条件を明示してフェーズ 1 の計画に載せ、承認ゲートで確認する。

詳細な取得手順・issue 特有の落とし穴は `references/issue-fetch.md` を参照。

---

## フェーズ 0.5: リポジトリ規約の把握

このスキルはリポジトリ非依存なので、**決め打ちせず読み取る**。手順とコマンドは `references/repo-conventions.md` にまとめてある。
最低限これだけは確定させてからフェーズ 1 に進む:

- **ベースブランチ**（`main` / `develop` / その他）
- **ブランチ命名・コミット規約**（Conventional Commits か、issue 番号を含めるか）
- **PR テンプレート**の有無と項目
- **Draft で CI が走るか**
- **ローカル検証コマンド**（lint / test / format）

読み取れなかった項目は、憶測で埋めずフェーズ 1 の「不明点」としてユーザーに聞く。

---

## フェーズ 1: 影響調査 → 実装計画 →【承認ゲート】

ここがこのスキルの肝。**コードを読んでから**計画を立てる。憶測で計画しない。

1. issue の要件に関係するコードを実際に調べる。広く当たる必要があるときは `Explore` / `general-purpose` サブエージェントに
   委譲してメインコンテキストを守る。
   - どのモジュール・ディレクトリが対象か
   - 既存の類似実装・パターン・命名規約
   - リポジトリの実装ガイド（`CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` / `docs/`）で該当する箇所
2. **不足情報があればこのタイミングでユーザーに質問する**（曖昧な仕様、未定義の受け入れ条件、複数の解釈が成り立つ箇所、
   設定値や環境変数の追加要否など）。実装を始めてから聞くと手戻りになる。
   issue 起票者と実装者が別人のことが多いので、issue 本文だけでは決まらない判断は積極的に上げる。
3. **検証可能性とサイズを評価する（このスキルとの相性チェック）**: このスキルは「実装 → ローカルで動作証明 → ゼロベースレビュー → 1 つの Draft PR」
   を前提にしている。次のいずれかに当たる issue は前提と噛み合わないので、計画と一緒に正直に申し送り、
   スコープの縮小・分割・別アプローチを提案する:
   - **ローカルで検証できない**変更（CI ワークフロー、リリース自動化、外部インフラ・権限に依存する変更など）
   - **flaky リスクや本番環境でしか確認できない**変更
   - **1 つの安全な PR に収まらない**規模（複数サブシステムにまたがる、エピック相当）→ 最小の意味あるスライスを提案する
   - **そもそも仕様の議論が先に要る** issue（「〜すべきでは？」という提案段階のもの）→ 実装ではなく論点整理を返す
   無理に進めず、ユーザーに判断を委ねるのが正しい挙動。
4. 次のフォーマットで**実装計画を提示し、承認を求めて必ず止まる**:

```
## 実装計画: #<番号> <タイトル>

### issue 理解
<2〜4 行の要約 / 受け入れ条件（issue に無ければ自分が置いた前提を明示）>

### 対象モジュールと変更方針
- <module>: <何をどう変えるか>

### 変更予定ファイル
- path/to/file: <変更内容>

### 確認したガイドライン / 既存パターン
- <準拠する規約・参考にした既存実装>

### 不明点・確認したいこと（あれば）
- <質問>

### ブランチ名（予定）
<prefix>/<issue番号>_<description>  ※リポジトリの命名規約に合わせる
```

ユーザーが OK を出すまで先に進まない。修正要望があれば計画を直して再提示する。

---

## フェーズ 2: ブランチ作成

承認が得られたら作業ブランチを切る。ベースはフェーズ 0.5 で確定したブランチ（最新を取得してから分岐する）。

```bash
git fetch origin <base>
git switch -c <prefix>/<issue番号>_<short_description> origin/<base>
```

- 命名はリポジトリの既存ブランチに倣う（`git branch -a` の傾向を見る）。規約が無ければ
  `<type>/<issue番号>-<short-description>` のような、issue 番号が入って追跡できる形にする。
- ベースブランチ直上で作業を始めていないか、別件の変更が混ざっていないかを確認する。
- 並行作業がある環境では worktree で分離するとディレクトリの取り合いを避けられる。

---

## フェーズ 3: 実装（+ ローカル検証）

1. 計画に沿って実装する。既存パターン・命名・コメント密度に合わせ、周囲のコードと地続きに見えるコードを書く。
2. リポジトリの実装ガイド（フェーズ 0.5 / 1 で読んだもの）に沿う。
3. **テストを作り切る**: 追加・変更した分岐をカバーするテストを、そのリポジトリの既存慣習（配置・命名・アサーション）に合わせて書く。
4. **push 前にローカル検証を回す**。Draft で CI が走らないリポジトリでは、ここが唯一の自動検証になる。
   フェーズ 0.5 で特定したコマンドのうち、変更したモジュールに対応するものを実行する（format → lint → test の順が無難）。
   検証コマンドが存在しない／通らないときは、通らない事実と理由を隠さずユーザーに報告する。

pre-commit フック（Lefthook / husky 等）が一部を自動でやることもあるが、それに頼り切らず明示的に回して結果を確認する。

---

## フェーズ 4: Draft PR 作成

1. リポジトリの規約に沿ってコミットする（Conventional Commits が使われているならそれに合わせる）。
2. **Draft** で PR を作成する。本文はリポジトリの PR テンプレートを埋め、issue へのリンクを必ず入れる。

```bash
git push -u origin <branch>
gh pr create --draft --base <base> --title "<規約に沿ったタイトル>" --body-file <path-to-body.md>
```

- 本文には `Closes #<番号>`（または `Fixes #<番号>`）を入れる。マージ時に issue が自動クローズされ、追跡が切れない。
  自動クローズさせたくない issue（親 issue・複数 PR に分割など）は `Refs #<番号>` にして、その旨を本文に書く。
- 本文はファイルに書いてから `--body-file` で渡すと崩れにくい。
- タイトル規約（`semantic-pr` / `pr-title-linter` 等の lint）があればそれに従う。

作成後、PR の URL をユーザーに伝える。PR 本文の組み立て方は `references/repo-conventions.md` を参照。

---

## フェーズ 5: ゼロベースレビュー → 反証 → 修正 → push（ループ）

このループの設計と判定基準の詳細は **必ず `references/review-loop.md` を読んでから**実行する。要点だけ：

1. **ゼロベースレビュー**: 独立したサブエージェント（実装の文脈を持たない）に「PR の diff」と「issue の要件」「リポジトリの実装ガイド」を渡し、
   先入観なくレビューさせる。このとき「良さそうか」を確認させるのではなく、
   **実装が壊れる具体的な入力・状態を能動的に探させる（敵対的検証）**。
   各指摘には重大度（`blocker` / `critical` / `major` / `minor` / `nit`）と
   **失敗シナリオ（具体的な入力/状態 → 誤った結果）**を必ず付けさせる。
2. **指摘の反証**: 出てきた指摘をそのまま信じない。`blocker` / `critical` / `major` は別のサブエージェントに**反証を試みさせ**、
   実コードで再現できない指摘（誤検知）を落とす。生き残った指摘だけを修正対象にする。
3. **修正**: 生き残った `blocker` / `critical` / `major` を修正する。`minor` / `nit` は妥当なら直し、見送る場合は理由を残す。
4. **push**: 修正をコミットして push する（Draft のまま）。push 前にローカル検証を回す。
5. **ループの停止条件**（無限ループ・過剰修正を防ぐ）:
   - `blocker` / `critical` が 0 になったら終了。残った `major` 以下はユーザーに一覧で報告する。
   - **最大 3 ラウンド**で打ち切る。3 ラウンドで `blocker`/`critical` が消えない場合は、残課題と原因の見立てを添えて
     ユーザーに判断を委ねる（堂々巡りや過剰修正のサイン）。
   - ラウンドごとに「今ラウンドの指摘・反証結果・対応・残件」を 1 ブロックで要約し、進捗が見えるようにする。

---

## フェーズ 6: 完了報告

最後に次を 1 メッセージでまとめる:

- Draft PR の URL
- 実装サマリ（何をどう変えたか）
- ローカル検証の結果（通ったテスト/lint。回せなかったものがあればその事実も）
- レビューループの結果（解消した重大指摘、反証で落とした誤検知、残した minor/nit とその理由）
- ユーザーへの申し送り（手動確認が要る点、スクショが必要な確認項目、Draft 解除の判断など）

---

## 安全策

- **破壊的・外部影響のある操作は確認してから**: `git push --force`、保護ブランチへの直接 push、PR の ready 化（Draft 解除）、
  マージ、issue のクローズやラベル変更は勝手にやらない。ユーザーの明示指示があるときだけ。
- このスキルが作るのは常に **Draft** PR。レビュー依頼（Draft 解除）はユーザーの判断に委ねる。
- 他人の issue にコメントを書き込まない（外部から見える発言になるため、必要ならユーザーに文面を提示して確認を取る）。
- 途中で計画と現実が大きくズレたら、無理に進めずフェーズ 1 に戻って再計画する。

## 参照ファイル

- `references/issue-fetch.md` — issue の取得手順（gh コマンド・参照形式の解決・関連 issue/PR の辿り方）
- `references/repo-conventions.md` — リポジトリ規約の自動検出（ベースブランチ・命名・PR テンプレート・Draft と CI・検証コマンド）
- `references/review-loop.md` — ゼロベースレビューと敵対的検証のサブエージェント指示・重大度ルーブリック・停止条件
